# LUCOUS Phase 3.4 — Technical Requirements Document (TRD)
## Architecture, Backend Services, Frontend Workflows & Security Specifications

### 1. Architectural Overview
Phase 3.4 connects teacher-curated content (Phase 3.2 lesson drafts and Phase 3.3 assessments) to the student learning experience via a controlled publishing workflow and cryptographic access codes.

```
+-----------------------------------------------------------------------------------+
|                              TEACHER WORKFLOW                                     |
|  [Review & Edit Drafts] -> [Publish Confirmation] -> [Server Generates AccessCode] |
|                                                              |                    |
+--------------------------------------------------------------|--------------------+
                                                               | (LU-XXXXXX)
                                                               v
+-----------------------------------------------------------------------------------+
|                              STUDENT WORKFLOW                                     |
|  [Enter Code /student/access] -> [Validate & Sanitize Payload] -> [Interactive UI] |
|                                                                                   |
|  Interactive Practice: [Submit Student Answer] -> [/check-answer] -> [Feedback]   |
+-----------------------------------------------------------------------------------+
```

### 2. Frontend & Backend Responsibilities
#### Backend Responsibilities
1. **Ownership & Access Control:** Ensure only authenticated teachers (`req.user.role === "TEACHER"`) can list, edit, publish, or unpublish their own drafts.
2. **Authoritative Code Generation:** Never accept a client-generated access code. Generate a 6-character uppercase alphanumeric code using Node.js `crypto.randomInt()`, with collision retry and database uniqueness.
3. **Payload Sanitization:** When returning content to students via access codes, completely strip:
   - Teacher IDs and private teacher details
   - Internal Mongo ObjectIds / paths
   - Source document raw text and storage keys
   - Correct answers and answer keys (for assessments and review questions)
4. **Server-Side Answer Evaluation:** Evaluate student responses securely via `POST /api/student/access/check-answer`, preventing client inspection of correct answers in the browser network tab.
5. **Rate Limiting:** Protect `/api/student/access/*` with an IP-based sliding window limiter (max 25 attempts/minute) to prevent brute-force code enumeration.

#### Frontend Responsibilities
1. **Teacher Content Review Experience:** Rich editing forms for lessons and assessments, draft status badges (`Draft`, `Reviewed`, `Published`), and clear feedback states.
2. **Publishing Dialog & Access Code Display:** Dialog presenting content metadata, publish confirmation, and on success, instant display of `LU-XXXXXX` with 1-click copy and shareable URL.
3. **Teacher Published List:** Table of published content with active access codes, copy actions, and unpublish revocation.
4. **Student Access Form:** Normalized code input (auto-uppercase, auto-formatting, dash handling), URL query param prefill (`?code=...`), and actionable error messages.
5. **Interactive Lesson/Assessment Viewer:** Responsive viewer rendering learning objectives, step-by-step explanations, real-world examples, glossary of terms, and interactive questions with instant answer feedback.

### 3. Access Code Cryptography & Collision Resilience
- **Alphabet:** 31 unambiguous alphanumeric characters:
  `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (excludes confusing `0, O, 1, I, L`).
- **Entropy:** $31^6 \approx 887,503,681$ unique combinations.
- **Prefix:** Standardized as `LU-` prefix with 6 characters (e.g., `LU-7K9M2P`).
- **Generation Logic:** `crypto.randomInt(0, ALPHABET.length)` ensures cryptographic uniformity.
- **Collision Retry:** In the unlikely event of a code collision, the backend retries up to 10 times with fresh random seeds before throwing an error.
- **Normalization:** Student input is cleaned: spaces and dashes stripped, converted to uppercase, prepended with `LU-` if entered as 6 characters without prefix.

### 4. Publishing Lifecycle State Machine
```
[DRAFT] <-----> [REVIEWED] -----> [PUBLISHED] -----> [REVIEWED / DRAFT]
  (Generated)    (Edited/Saved)    (Active Code)        (Unpublished/Revoked)
```
- **DRAFT:** Newly generated by AI or teacher edits in progress. Inaccessible to students.
- **REVIEWED:** Teacher has verified and approved content. Inaccessible to students.
- **PUBLISHED:** Teacher explicitly confirmed publication. Has unique `accessCode` and `publishedAt`. Publicly accessible to students with valid code.
- **UNPUBLISHED:** Content reverted to `REVIEWED`. `accessCode` cleared and `publishedAt` nullified. Student access immediately terminates.

### 5. Security & Privacy Matrix
| Aspect | Policy |
|---|---|
| Cross-Teacher Isolation | Filter all queries with `teacherId: req.user.id`. Reject with 403/404 if mismatch. |
| Student Data Isolation | Student endpoints require zero authentication to maximize educational reach, but never leak teacher or user details. |
| Answer Key Protection | `correctAnswer` omitted from student payloads. Checked exclusively on backend. |
| Code Enumeration | IP sliding-window rate limit (25 req/min). Non-existent codes return generic 404. |
| Input Normalization | Regex sanitization strips control characters and validates payload schemas. |
